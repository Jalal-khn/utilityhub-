## What a QR code actually is

A QR code is a two-dimensional barcode: a grid where each black or white square represents data bits. Unlike the old supermarket barcode that holds about twenty digits, a QR code can store thousands of characters - enough for a full web address, WiFi credentials, or a paragraph of text.

Three facts worth knowing before you generate one:

1. **A static QR code never expires.** The pattern *is* the data. Nothing points back to any company's server, so no subscription can switch it off.
2. **More data means a denser code.** A short URL produces large, easy-to-scan squares; a long, parameter-heavy URL packs tighter and needs better lighting to scan.
3. **The camera decides everything.** QR reading happens on the scanning phone, so print quality and size matter more than which generator you used.

## Choosing the right size

Size failures are the number one reason printed codes disappoint. The practical rule: **the QR code should be about one twenty-fifth of the expected scanning distance.**

| Scanning distance | Minimum code width |
| --- | --- |
| 25 cm (business card) | ~1-2 cm |
| 50 cm (letterhead, packaging) | ~2-3 cm |
| 1 m (table tent, shelf label) | ~4-5 cm |
| 3 m (poster, storefront) | ~12+ cm |

Two supporting details matter as much as raw size. First, **shorter content means bigger modules** - the individual blocks inside the code stay chunky and scannable, which is one more reason to keep destination URLs short. Second, preserve the **quiet zone**: the blank margin around the code is part of the standard, and cropping it tight against artwork degrades scan reliability even when the code itself looks perfect.

## Static versus dynamic codes: why it matters for "free"

QR services fall into two families, and choosing wrong is the most expensive mistake in this space:

**Static codes** encode your destination directly into the pattern. The data lives in the image itself - permanently. Generate it, print it, forget it; the code functions identically in year ten as in day one, with no account, no invoice, no dependency.

**Dynamic codes** encode a redirect address owned by the service. The service logs scans and can change the destination later - genuinely useful for marketing teams tracking campaigns - but the flip side is structural: stop paying, and every printed code you ever made stops working.

Many "free QR generator" websites generate static-looking codes through dynamic infrastructure, then email renewal notices months after your flyers have shipped. When you only need the destination to stay put, insist on true static generation like the browser-based approach described above - the code belongs to you outright because nothing but the pixels carries the data.

## Printing and placement best practices

- **Keep contrast high.** Dark code on a light background scans far more reliably than the reverse. White-on-black inverted codes fail on many readers.
- **Print a test scan** at final size before running a batch - what looks crisp on screen may blur on textured stock.
- **Avoid placing codes on curves, fabric, or glossy surfaces** that catch glare.
- **Mind the destination.** Point the code at a short, permanent URL - not a link that will break when a campaign ends.
- **Tell people what they get.** A caption like "Scan for the menu" measurably increases scans versus a bare code.

## Common mistakes to avoid

- **Using expired "free trial" generators** that quietly start routing (and charging for) your traffic - a truly static code has no such dependency
- **Encoding long tracking URLs**, producing dense codes that struggle in dim restaurants
- **Screenshotting a preview at low resolution** instead of downloading the full-size PNG
- **Printing dark-on-dark or inverting colors** for style
- **Forgetting the test scan** - always scan your own code with two different phones before it ships
- **Pointing codes at pages destined to move** - link to a permanent URL you control and redirect from there, so printed materials survive website redesigns

## Troubleshooting a stubborn code

When a code refuses to scan, work through the usual suspects in order:

1. **Distance-to-size mismatch** - the most common cause; hold the phone closer or reprint larger
2. **Insufficient contrast** - light codes on dark backgrounds, or code-on-pattern artwork, defeat many readers
3. **Blur** - screenshots of screenshots, aggressive image compression, or stretching beyond the download resolution
4. **Damaged quiet zone** - the white margin got cropped, framed too tightly, or printed over a busy background
5. **Glare** - glossy lamination directly over the code turns into a mirror under indoor lighting

Fixing almost any of these takes less time than diagnosing why customers stopped scanning - which is exactly why the test scan belongs in every workflow before printing.
